### 1.2 消息格式：OneBot 11

- NapCat 对 OneBot 11 的 WebSocket 支持：事件（`message`/`notice`/`meta_event`）与 Action API（`send_group_msg`、`get_image`、`get_record` 等）均为 JSON，字段包含 `message_id`、`group_id`、`user_id`、`sender`、`message`（消息段数组：`text`/`image`/`file`/`at` 等）。
- 本项目只需消费：群消息事件（文本、@全体、图片、文件段）+ 少量发送 API（可选的确认/回执消息）。

综合结论：**无成熟、活跃、被广泛验证的 OneBot 11 C# SDK**（所谓 "OneBot.Get/NHahu" 未在 GitHub/NuGet 检索到成熟维护的项目）。

### 1.4 最终选择：**自写薄 WebSocket 客户端 + OneBot 11 事件 DTO（自研，代码量可控）**

理由：
1. 本项目对 OneBot 11 的消费面极窄（群消息事件 + 2~3 个 Action），一个基于 `System.Net.WebSockets.ClientWebSocket` + `System.Text.Json` 的客户端约数百行即可覆盖，无外部依赖；
2. 现有 C# SDK 均不成熟（Star 数与维护活跃度不足以承担长期依赖），引入反而增加不可控风险；
3. 自写客户端便于实现本项目特有的**指数退避重连、消息幂等（message_id 去重）、重试队列**等降级需求，这是成熟 SDK 也需要二次封装的部分；
4. 协议端（NapCat）与插件解耦：插件只依赖 OneBot 11 JSON 契约，未来可无痛切换 Lagrange.OneBot 等其它协议端。

## 2. WPF/悬浮窗（无边框置顶、拖拽、缩放）

**前提修正**：ClassIsland master 的 UI 是 **Avalonia**，WPF 系库对本项目不可用（除非回退目标 1.x 稳定版，已排除）。因此以下评估按 Avalonia 语境给出，WPF 候选仅作背景。

| 候选 | 适用性 | 评估 |
| --- | --- | --- |
| WindowChrom / WPF 无边框库 | ❌ WPF 专用 | 不适用 |
| GongSolutions/WPF.DragDrop（~7k+ Stars，MIT，维护趋缓） | ❌ WPF 专用，且职责是列表拖放而非窗口拖动 | 不适用 |
| **Avalonia 原生能力（手写）** | ✅ | **首选**（见下） |

**最终选择：手写 Avalonia 悬浮窗（零第三方依赖）**：
- 无边框置顶：`SystemDecorations="None"` + `Topmost=true` + `ShowInTaskbar=false` + `TransparencyLevelHint="Transparent"`；
- 拖拽：`PointerPressed` 中调用 `window.BeginMoveDrag(args)`（Avalonia 原生 API，等价 WPF 的 `DragMove()`）；
- 缩放：角部 `Thumb`/`Splitter` + `PointerMoved` 调整 `Width/Height`（或 `LayoutTransformControl` 缩放内容）；
- 位置/大小/透明度/字号持久化到插件设置 JSON，`ISuspensionWindowController` 提供"复位默认"。

理由：Avalonia 原生 API 已完整覆盖需求；悬浮窗逻辑（拖动、缩放、记住位置）总量极小，引入第三方库的收益低于其兼容性风险。

## 3. MD5 计算与去重

| 候选 | 评估 |
| --- | --- |
| **System.Security.Cryptography.MD5 / MD5.Create()（.NET 内置）** | ✅ **选择**。流式计算（`TransformBlock/TransformFinalBlock` 或 `ComputeHash(stream)`）即可处理大文件；`System.IO.Hashing`（XxHash）更快但 MD5 是本项目的既有去重键约定，且无需安全性 |
| 第三方（如 hashids、MD5 库） | ❌ 无必要 |

理由：内置即可，零依赖。文件去重键 = `MD5(文件内容)` + 文件大小双校验；消息幂等键 = OneBot `message_id`（不需要 MD5）。ClassIsland 核心库也有 `ChecksumHelper`（用于校验下载文件），可参考但其 API 面向更新器，不复用。

## 4. 轻量文本分类 / AI 识别（三级学科识别链）

设计为三级链：**①关键词规则（SubjectRule）→ ②本地 ONNX 小模型 → ③云端 LLM API（可选）/人工确认**，置信度逐级传递，低置信度进 `PendingConfirmItem` 人工确认队列。

| 层级 | 候选 | Stars/维护 | License | 评估与选择 |
| --- | --- | --- | --- | --- |
| ② 本地模型运行时 | **Microsoft.ML.OnnxRuntime** | ~21,754 / 活跃（2026-09 仍有提交） | MIT | ✅ 选择。C# API 成熟（`InferenceSession`），CPU 包体积可控（约 30MB 级），与 net8.0 兼容 |
| ② 中文文本小模型 | 中文 BERT 蒸馏/小模型导出 ONNX（如 RBT3、albert_tiny、fastText 分类器），经 `optimum`/`torch.onnx.export` 导出 | HuggingFace 社区 | 模型各异（多为 Apache-2.0） | ✅ 可行。中文 3 分类/12 分类小模型（~20-100MB）在 CPU 上单条推理 <50ms；模型文件随插件分发或首次使用时下载 |
| ③ 云端 LLM | OpenAI 兼容 API（DeepSeek/通义/自建网关），HTTP 调用，无需专用 SDK | — | — | ✅ 备选，默认关闭。仅当 ①② 均低置信且用户在设置中启用时调用；走 `System.Net.Http.HttpClient` + JSON |
| ① 关键词规则 | 自研（SubjectRule 关键词/正则 + 权重） | — | — | ✅ 基础层，零依赖、可解释、可编辑，覆盖绝大多数常规通知（"明天交数学作业"等） |

理由：课堂场景文本高度模式化，关键词规则即可覆盖大半流量；ONNX 小模型作为兜底提升召回；LLM 成本与隐私（学生 QQ 消息出校）风险使其只作为可选项——因此本地方案必须以"关键词+规则可完全手动兜底"为设计底线。

## 5. 配置持久化

| 候选 | 评估 |
| --- | --- |
| **JSON（System.Text.Json）+ 插件配置目录** | ✅ **选择**。与 ClassIsland 全家桶风格一致（宿主 `SettingsService` 即 JSON 文件）；插件拥有独立 `PluginConfigFolder`；数据规模（通知/作业条目、文件索引）在校内场景为每天几十条量级，JSON 完全够用 |
| ClassIsland 现有 SettingsProvider 复用 | ❌ 主程序设置是单一 `Settings.json` + `SettingsService`（内部类型），**没有**可复用的泛型 `SettingsProvider<T>` 公共组件；且其 Settings 类型含宿主全部配置，不适合插件复用。插件遵循生态惯例自管配置文件 |
| SQLite（Microsoft.Data.Sqlite） | ⚠️ 保留为升级路径。若后续需要跨学期检索、按内容全文查询、消息量达万级，再引入（MIT，net8.0 兼容）；契约层（INoticeStore/IHomeworkStore）已按存储无关设计，切换不影响其它模块 |

**最终选择：JSON 持久化（分文件：notices / homework / files / settings），SQLite 不引入。**

## 6. 打包分发

| 候选 | 评估 |
| --- | --- |
| **dotnet build 产出 .cipx 插件包（ClassIsland.PluginSdk.targets，`CreateCipx=true`）** | ✅ **选择（插件本体）**。与 ClassIsland 插件生态原生一致，可直接放入 `Plugins` 目录或经插件市场分发 |
| dotnet publish 自包含单文件 | ⚠️ 仅当出现"独立协议端接入器进程"（把 WebSocket 客户端拆出宿主）时才需要；插件形态不需要。若拆分，接入器用 `dotnet publish -r win-x64 --self-contained -p:PublishSingleFile=true` |
| GitHub Actions | ✅ **选择（CI）**。矩阵构建 + 上传 .cipx artifact + Release 发布 |
| Inno Setup（jrsoftware/issrc，~5,610 Stars，Inno License（免费开源），活跃） | ❌ 模块 0 阶段不需要：插件不是安装程序形态；仅当未来做"协议端+插件"一体化安装器时再评估 |

**最终选择：插件包 = .cipx（dotnet build）；CI = GitHub Actions；不引入 Inno Setup。**

## 选型汇总

| 类别 | 最终选型 | 一句话理由 |
| --- | --- | --- |
| QQ 协议端 | NapCat（独立进程，OneBot 11） | 最活跃、适配最完整的 OneBot 11 协议端 |
| OneBot 接入 | 自写 WebSocket 客户端 | 消费面窄、现有 C# SDK 不成熟，自写可控且便于实现重连/幂等 |
| 悬浮窗 | Avalonia 原生手写（无边框+BeginMoveDrag+Thumb 缩放） | master 是 Avalonia；原生 API 已覆盖，无需第三方库 |
| MD5/去重 | .NET 内置 System.Security.Cryptography | 零依赖，流式支持大文件 |
| 文本分类 | 关键词规则 + Microsoft.ML.OnnxRuntime 中文小模型 + 可选 LLM | 规则覆盖大头，本地模型兜底，LLM 可选控制成本与隐私 |
| 持久化 | System.Text.Json 分文件持久化 | 与宿主风格一致，量级足够；契约层为将来 SQLite 留口 |
| 打包 | .cipx + GitHub Actions | 与插件生态原生一致 |
