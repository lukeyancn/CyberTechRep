# QQ 群消息接管方案调研：零风控路线对比（2026-09）

> 调研目标：为 ClassIsland 插件「QQ 群消息接管与课堂信息分发系统」选定接收指定 QQ 群全部消息（文本/图片/文件，含非 @ 普通发言）并自动下载群文件的路线，优先保证**账号零风控风险**。
> 信息来源：QQ 机器人官方文档（bot.q.qq.com/wiki，2026-07 更新版）、GitHub 仓库 API 实测数据、社区事件记录（linux.do、ippclub、NapCatQQ issues）。检索日期：2026-09-03。

---

## 一、最重要的结论（先说答案）

**存在。2026 年的 QQ 官方机器人开放平台已经可以"不 @ 即接收全部群消息（含图片/文件附件）"，且这是唯一真正零风控风险的路线。**

官方文档（2026-07-23 更新）新增了 `GROUP_MESSAGE_CREATE` 事件，官方名称为「**群消息（全量模式）**」：

> 「当机器人开启了"接收所有消息"功能后，群里的每一条消息（不限于@机器人）都会推送此事件。各字段含义与 GROUP_AT_MESSAGE_CREATE 完全一致。」

该事件与 @ 消息事件共用同一套事件体，`attachments` 数组携带 `image/jpeg`、`image/png`、`video/mp4`、`voice` 以及 **`file`（群文件）** 类型的附件，且每个附件带直接下载 URL（`multimedia.nt.qq.com.cn` 域名 + rkey 签名）。第三方项目（如 OpenClaw 的 QQ 适配器）已在生产环境使用此能力，佐证其真实可用。

**开通条件**：群主在机器人管理页开启「接收所有消息」开关；机器人声明 `GROUP_AND_C2C_EVENT (1<<25)` Intent 即可收到。个人开发者即可申请机器人并使用群聊场景（2024 年中起官方对个人开发者开放群聊/单聊，企业认证只提高频控配额，不是准入门槛）。

以下按路线详述能力边界。

---

## 二、路线 1：QQ 官方机器人开放平台（q.qq.com）

### 2.1 准入与进群

- **注册**：任何人在 q.qq.com 注册即可创建机器人（个人主体可选），获得 AppID/AppSecret。
- **进群**：必须由**群主或管理员**在 QQ 客户端「群聊设置 → 群机器人 → 添加机器人」操作；官方有对应的 `GROUP_ADD_ROBOT` 事件。个人无法把机器人拉进自己不是管理的群。对课堂场景，班主任/老师（通常为群主）操作一次即可。
- **上线审核**：机器人正式使用需通过平台的上线审核（名称、头像、功能描述、内容合规）；开发期可用沙箱环境。

### 2.2 消息接收能力

| 能力 | 状态 | 说明 |
| --- | --- | --- |
| @机器人 消息 | ✅ | `GROUP_AT_MESSAGE_CREATE`，最基础事件 |
| **全部群消息（不@）** | ✅（2026 新增） | `GROUP_MESSAGE_CREATE` 全量模式，需群主开启「接收所有消息」 |
| 图片 | ✅ | attachments 携带直链（含 rkey），可直接下载 |
| 文件 | ⚠️ 部分 | 消息中发送的文件（attachments `content_type=file`）可收到并下载；**"群文件面板"里直接上传、未以消息形式出现的内容没有推送事件，也没有群文件列表/下载 API** |
| 视频/语音 | ✅ | 语音还带 SILK→WAV 转换 URL 和 ASR 参考文本 |
| 撤回/引用/合并转发/卡片 | ✅ | msg_elements 支持 message_type=102（聊天记录）、103（引用）、ark 卡片 |
| 标识符 | ⚠️ | 全部使用 OpenID（群 openid、成员 openid），**拿不到真实 QQ 号码**；用户昵称可获取，群内角色（owner/admin/member）可获取 |

### 2.3 发送能力与限制

- **被动回复**（携带 msg_id）：群聊有效期 **5 分钟**，每条消息最多回复 **5 次**。做"作业确认回执"足够。
- **主动消息**：未认证 30/qpm、认证 60/qpm（bot 维度），单群每日上限 **1000 条**；用户可关闭「允许主动发送」导致发送失败。课堂通知场景（每天几条）完全够用。
- **富媒体发送**：支持 msg_type=7，图片/视频/语音/**文件**均可先分片上传取 `file_info` 再发送（单聊、群聊上传接口不互通，`file_info` 有 TTL）。**发文件没问题**。
- **Markdown**：msg_type=2 需要 markdown 模板/权限申请，未申请只能发纯文本和富媒体。本项目可用纯文本+图片规避。

### 2.4 SDK / .NET 生态

- **官方 SDK**：Go（tencent-connect/botgo）、Python（botpy）、Node.js（bot-node-sdk）。**无官方 C# SDK**。
- **GitHub C#/.NET 第三方**：
  - `XeronOwO/QQBot4Sharp`：14 star，MIT，**已归档**（最后推送 2024-03）。
  - `ZiYuKing/QQBot.NET`：其 fork，1 star，2024-10 后停更。
  - 均未覆盖 2026 年的 `GROUP_MESSAGE_CREATE` 全量事件，**不建议直接依赖**。
- **结论**：官方接入协议本身很简单（AppSecret 换 Access Token + WebSocket 网关/Webhook 回调 + REST 收发），ClassIng 是 .NET 项目，**自写一个几百行的薄封装**（或参考 QQBot4Sharp 的鉴权部分）是最现实的路径。

## 三、路线 2：NapCat / Lagrange 等非官方协议端

### 3.1 技术形态与本质差异

- **NapCat**（NapNeko/NapCatQQ，10.4k star，2026-08 仍活跃，自定义许可证——官方明确"仅用于消息推送类功能，禁止未授权二次封装"）：注入官方 NTQQ 客户端进程，协议/设备指纹是真实的，风控暴露面主要在**行为层**。
- **Lagrange.Core / LagrangeGo**（2.9k star，2026-09 仍活跃）：**从零实现 NTQQ 协议**（C#，衍生自 Konata.Core），非官方客户端，风控暴露面在**协议层**，历史上新设备登录触发滑块/冻结的概率高于 NapCat。仓库无标准开源许可证且有强免责声明。

### 3.2 风控事实（2025–2026）

- **封号案例真实存在**：NapCatQQ issue #750（2025-02）："每次挂了三天左右就会被腾讯限制产品功能，需要去手机端确认解除"；维护者的官方答复是"这种并非 NapCat 的问题，若不想被封号，只能建议你别用"——即**维护者自己承认账号风险不可避免**。
- **2025-09-05 大规模事件**：公网上大量未设 token 的 OneBot 服务（NapCat 默认监听 0.0.0.0）被攻击者批量调用发布敏感信息，导致大量机器人账号和群聊被封；**腾讯随后加严了反机器人策略**（linux.do 综述帖）。这不是协议被识别的直接证据，但显著提高了整体风控敏感度。
- **社区低风控实践**（可降低、不能消除风险）：只用小号且与主号隔离、在常用设备/常用地长期在线、避免高频发送与群发、设置 OneBot access token 并收紧监听、只加少量群。
- **"仅接收不发送"的影响**：被动接收确实比高频发送安全得多，但登录行为本身（非官方注入/协议）就违反 QQ 用户协议，腾讯保留随时冻结账号的权利，**风险是持续存在的，不是零**。

### 3.3 对"小号只收不发"的评级

低频、单群、长期在线的老小号 + NapCat，是目前社区公认**最稳的非官方姿势**，实际冻结率无权威统计（社区样本看是"个位数月内可能遇到一次限制功能、可手机端解除"量级），但**不满足"零风控"要求**，且风险全部由登录账号承担。

## 四、路线 3：其他替代方案核实

| 方案 | 能否收全部群消息 | 核实结论 |
| --- | --- | --- |
| 企业微信群机器人（官方） | ❌ | 群聊中同样**只有 @机器人 的消息**才推送到 webhook；且企业微信不是 QQ，学生/老师需迁移平台，不可行 |
| 钉钉自定义机器人（官方） | ❌ | 同样只有 @消息 才有 outgoing 回调；非 QQ 生态 |
| QQ 频道机器人（官方） | ⚠️ | 文字子频道可以收全量消息，但"频道"是与 QQ 群完全不同的产品形态，班级场景用不上；频道生态近年持续收缩 |
| 声称"无风险"的开源方案 | ❌ | OpenShamrock（已停更）、LLOneBot、LiteLoaderQQNT 系插件等，本质都是 **NTQQ 注入 hook（NapCat 同类）或独立协议实现（Lagrange 同类）**，没有任何项目真正规避了非官方协议——所谓"无风险"只是风险更低的运营姿势，属"换皮"而非豁免 |

## 五、结论矩阵

| 路线 | 接收全部群消息（不@） | 群文件接收 | 风控风险 | 接入难度 | 满足核心需求程度 |
| --- | --- | --- | --- | --- | --- |
| **官方平台 + 全量模式（GROUP_MESSAGE_CREATE）** | ✅ | ✅ 消息内文件（❌ 群文件面板浏览） | **零**（官方通道） | 中（注册审核 + 群主配合 + 自写 .NET 薄 SDK） | ★★★★★（群文件面板例外） |
| 官方平台 + 仅 @ 消息 | ❌ 仅 @ | ✅ @ 消息内附件 | 零 | 低-中 | ★★★（依赖课代表/老师 @） |
| NapCat（小号、被动接收） | ✅ | ✅ 含群文件面板 | 中（真实封号/冻结案例，违反用户协议） | 低 | ★★★★（功能全但违约且有风险） |
| Lagrange（C#，独立协议） | ✅ | ✅ 含群文件面板 | 中偏高（协议层暴露 + 无正式许可证） | 中 | ★★★☆ |
| 企业微信/钉钉机器人 | ❌ | ❌ | 零 | 低 | ★（非 QQ 且收不到全量） |
| 各类"无风险"开源方案 | ✅ | ✅ | 中（均为非官方协议换皮） | 低-中 | ★★★（不满足零风控前提） |

## 六、对 ClassIng 的落地建议

1. **主路线：官方机器人 + 全量模式。** 满足"不 @ 即收全部群消息 + 图片/文件附件直链下载 + 零风控"。需要的前置配合：老师/群主把机器人拉进班级群，并在机器人管理页打开「接收所有消息」。.NET 侧自写 WebSocket/REST 薄封装（无可用且在维护的 C# SDK）。
2. **明确的残余缺口（必须告知用户）**：
   - **群文件面板**：官方没有"列出/下载群文件区所有文件"的 API。通过聊天消息发到群里的文件可以收到并自动下载；但同学直接丢进群文件面板且未产生聊天消息的文件收不到。缓解：群规要求"交作业请发到群里/发文件时 @机器人"，或对班级群而言消息内文件已覆盖绝大多数场景。
   - **OpenID 匿名**：拿不到成员真实 QQ 号，需用昵称/member_openid 建立课代表映射（在群内让课代表 @机器人 报到一次即可绑定）。
   - **主动消息**：单群每日 1000 条、用户可关闭接收——课堂通知量级无压力。
3. **兜底路线：@ 模式。** 如果群主不愿开全量开关，退化为"课代表/老师发作业时 @机器人"，功能依然成立（课代表配合成本极低），是否可接受由用户决策。
4. **不建议路线**：NapCat/Lagrange 满足功能但违反 QQ 用户协议、有真实封号案例与 2025-09 后加严的风控环境，与"零风控"的硬性要求冲突；仅可作为用户知情并自担风险时的备选。
