## 1. 连接状态机：反向监听循环把活动连接的状态打回「连接中」（含偶发失败根因）

**现象**：设置页/UI 的 NapCat 连接状态在「已连接」与「连接中」之间跳变；`NapCatConnectionStateTests` 偶发失败（每轮失败的具体用例不同）。

**根因**：
- `NapCatWsClient.RunReverseServerAsync` 的接受循环**每轮无条件**写 `SetStatus(Connecting)`（`NapCatWsClient.cs:458` 附近），
  而该循环在 accept 返回后会立刻转入下一轮——于是活动连接刚确认的
  `Authenticating` / `Connected` 会被这句覆盖，状态回跳。异步调度下覆盖时机随机，故表现为偶发失败
  （日志实证：`Connected` 之后紧跟 `Connecting`）。
- `Status` 是普通自动属性，被接收循环、监听循环、看门狗等多个后台线程写入，UI/测试线程读取——跨线程可见性没有保证。

**修复**：
- 状态改为 volatile 字段承载 + `Interlocked.Exchange` 写入（`NapCatWsClient.cs:103`、`:204`），跨线程读写无丢失更新/过期读。
- 反向监听循环只在「**没有任何连接在飞行中**（`_reverseLiveConnections == 0`）且当前状态属于
  `Disconnected`/`Connecting`」时才宣布「连接中」（`:458`）；连接数在接受后立即登记（`:480`）、
  处理结束归零（`:562`）。这样：
  - 活动连接的 `Authenticating`/`Connected` 不会被覆盖；
  - **鉴权失败（`AuthenticationFailed`）成为终态**，用户能在 UI 上看到失败原因（旧实现会被「连接中」盖掉）。

**回归测试**（`NapCatConnectionStateTests.cs`）：
- `已连接后_再接入未握手的连接_不得把状态打回Connecting`：**已验证**在旧行为下必然失败（1.66 s 稳定复现）。
- `token不匹配_状态置AuthenticationFailed`：补「600 ms 后仍是 `AuthenticationFailed`」的终态断言。

## 2. 作业文档：编辑态合并锚点改为「条目 id」——修掉改写旧行被重复追加

**现象（原审计报告的需求 1 缺陷延续）**：编辑期间新到的消息可能被编辑器防抖落档覆盖丢失；并且用户在编辑态
**改写**过的旧行会在下一次落档时被当成「新到的行」重新追加，文档出现重复行。

**根因**：三方合并用「进入编辑态时的渲染文本」做基线（`HomeworkStore.MergeLateLines` 旧实现），
而窗口每次落档成功后又把基线换成编辑稿（`HomeworkSuspensionWindow.axaml.cs` 的 `PersistDocumentTextAsync`）——
被改写的旧行文本既不在编辑稿里、也不在更新后的基线里，于是被判为「编辑期间新到」反复补齐。

**修复**：合并锚点改为**进入编辑态那一刻的条目 id 集合**（`knownEntryIds`，`Abstractions.cs:234` 附近）：
- 只有锚点**之外**的条目（= 编辑期间真正新落档的消息）才把行增量补进编辑稿；
- 锚点内条目（用户当时看到的旧行）的删、改一律尊重用户结果；
- 锚点在**整个编辑态期间不变**（落档后并入新条目会让下一拍把它们当旧行丢掉），
  窗口侧另行维护 `EditBaseline` 仅用于「有没有改动」的判定。
- 实现见 `HomeworkStore.cs:638`（`MergeLateLines`）、窗口 `HomeworkSuspensionWindow.axaml.cs:102`（锚点属性）、
  `:409`（进入编辑态时按文档条目标注锚点）、`:545-562`（落档时传锚点、更新基线）。

**回归测试**（`HomeworkDocumentStoreTests.cs` 新增 3 条）：
- `SaveDocumentText_DuringEdit_LateEntryIsMergedIntoEditorText`（编辑期间新消息不丢）；
- `SaveDocumentText_DuringEdit_RewrittenOldLine_IsNotReappended`（改写旧行不被重复追加）；
- `SaveDocumentText_DuringEdit_DeletedOldLine_StaysDeleted`（删掉的行不被补回来）。

## 3. 常态化作业：勾选态与当天文档事实一致；发送内容与预览同源

**现象**：确认浮层每次打开都把常态化作业重置为「未勾选」，但该条目若今天已经落档（已在学科文档里），
它本来就会随清单发出——界面与事实不一致，老师无法判断是否已计入；重复勾选还会让清单里出现两条同内容行。
另：一次发送必须与预览完全一致（落档后重新格式化会再追加一遍，是「发送内容里常态化作业重复」的根因）。

**修复**：
- 打开确认浮层时按当天文档计算「已落档」键（`CollectLandedStandingKeys`，`HomeworkSuspensionWindow.axaml.cs:717`）：
  已落档条目显示为**已勾选 + 不可取消**，文案标注「（今天已落档）」（`StandingHomeworkView.IsLanded`，`:166`）；
- 落档只针对本次新勾选的条目（已落档条目跳过，避免无谓写入）；
- 发送流程收口到 `ConfirmSendAsync`（`:815`）：**先取预览文本、再落档、最后发送**，发送的即预览字符串；
  浮层打开与预览刷新抽成 `OpenSendOverlay`（`:664`）/ `RefreshSendPreview`（`:734`）供测试驱动。

**回归测试**（新增 `StandingHomeworkLandingTests.cs`，窗口级 + 纯函数）：
- `已落档的常态化作业_显示为已勾选且不可取消_预览不重复`；
- `未落档的常态化作业_勾选后发送内容与预览一致且只出现一次_并落档`（含「落档后再打开一次」的二轮验证）；
- `CollectLandedStandingKeys_OnlyStandingEntriesOfMatchingSubject`（只算常态化条目、学科需一致）。

## 4. 通知↔作业互换：整篇文档迁移为**每一条**来源消息记录换类覆盖

**现象**：手工整理过的文档「转为通知」后，原消息重投/断点续传补齐时会在作业侧再次出现
（换类被回摆）；合并条目只记了第一条来源 id，其余来源 id 同样会被摆回作业。

**根因**：`MessageReclassifyService.MoveDocumentToNoticeAsync` 的手工文本分支完全不写覆盖记录
（只用合成键 `document:{date}:{subject}`），逐条分支只对「第一条非空来源 id」调用 `_overrides.Set`。

**修复**：
- 新增 `MessageKindOverrideStore.SetMany`（`MessageReclassifyService.cs:108`）：一次加锁、一次落盘，
  避免逐条落盘与「半个覆盖集」；
- 迁移前收集文档内**全部**来源消息 id，迁移后一次性写入覆盖（`:322` 起的 `sourceIds` + `SetMany`），
  手工文本分支同样生效。

**回归测试**（`MessageReclassifyServiceTests.cs`）：
- `MoveDocumentToNoticeAsync_ManualText_MigratesSingleNotice` 补「来源 id m5 已记覆盖」断言；
- `MoveDocumentToNoticeAsync_MergedEntry_RecordsOverrideForEverySourceMessage`（合并条目的两条 id 都记）。

## 5. 文件下载：瞬时失败自动重试 + HTTP Range 断点续传 + 失败进重试队列

**现象**：群里发的文件「有时候下载不下来」，且失败后没有任何自动恢复；用户问「文件是否有断点续传」。

**根因**：
- 下载只有**一次**尝试（`EnqueueAsync` → `DownloadAndArchiveAsync`），任何网络抖动/连接被断都会直接落
  `Failed` 并**删除半成品**，且管道不再自动重试（`RetryQueue` 的 `FileDownload` 只在「入队抛异常」时才投递，
  「下载失败」这条路径不投递）。
- `HttpClient.Timeout = 60 秒` 是**整个请求**的硬超时：大文件在慢链路上必然超时失败，且无续传。
- 没有 `Range` 续传：中断即从 0 重来。

**修复**（`FilePipelineService.cs`）：
- **自动重试**：单次入队最多 3 次尝试（`DownloadMaxAttempts`），瞬时失败（网络异常/连接被断/读取停滞/5xx）
  退避 1s、3s 后重试；4xx（直链过期被拒）、超单文件上限、磁盘策略拒绝为永久失败，不重试。
- **断点续传**：半成品按「记录 id」命名（`{根目录}/.download-{recordId}.tmp`，不再是随机名），重试时带上
  `Range: bytes=N-` 从已下载字节继续；服务器不支持续传（回 200）自动从头下，断点越界（416）丢弃半成品再来；
  MD5 续传时先用已有字节做前缀种子，保证归档文件的哈希覆盖完整内容；服务器声明了完整长度就做完整性对齐校验。
- **停滞超时取代总超时**：改用逐次读取的停滞上限（60 秒无新字节 = 连接僵死，按可重试失败处理），
  慢链路大文件不再因「总时长」被误判失败（`HttpClient` 不再设总超时）。
- **失败进重试队列**：新增 `FileRecord.FailureRetriable`；瞬时类失败用尽管道重试后仍为 `true`，
  消息管道据此投递 `FileDownload` 重试条目（`MessageDispatchService`），交给模块 8 队列按退避再试，
  并在排障面板可查看/手动重放；永久失败不投递（避免无意义退避与噪声）。

**回归测试**（`FilePipelineTests` +4 / `MessageDispatchServiceTests` +2）：
- `EnqueueAsync_DownloadInterrupted_RetriesWithRangeAndArchivesCompleteFile`（中断 → 续传 → 归档内容与 MD5 为完整文件）；
- `EnqueueAsync_ServerIgnoresRange_RestartsFromScratchWithoutCorruption`（服务端不支持续传时不产生拼接损坏）；
- `EnqueueAsync_DownloadInterrupted_RetriesThenFailsWithoutLeftovers`（3 次用尽 → Failed + `FailureRetriable` + 无残留）；
- `EnqueueAsync_HttpForbidden_IsPermanentAndNotRetried`（403 过期：1 次尝试、不可重试、提示「已过期」）；
- `FileDownload_RetriableFailure_QueuesFileDownloadRetry` / `FileDownload_PermanentFailure_DoesNotQueueRetry`。

## 6. 悬浮窗内容字号：正文（可选中/可编辑文本）显式跟随设置字号

**现象**：悬浮窗设置里的「字号」改了之后，通知窗的正文（可选中复制的只读文本）与作业窗的文档正文
（可选中/可编辑）看起来没变化。

**根因（说明）**：字号只设在**窗口**上（`SuspensionWindowController.ApplyToWindow` 的 `window.FontSize`），
而正文控件是否跟随完全依赖「属性继承能否胜出」——只要主题/样式在某层级给该类控件提供了字号，
它就会压过窗口级继承，正文不随设置变（同窗内没有显式字号的边角控件才会变）。这种依赖从插件侧无法保证，
因此改为**显式设置**：不论主题怎么写，正文都按设置字号渲染。

**修复**：
- 新增 `IOverlayContentFontSizeAware`（`Services/Overlays/`）：由控制器在每次应用设置时把字号转交给窗口
  （`SuspensionWindowController.ApplyToWindow`）；
- 通知窗与作业窗用「窗口资源 + 样式动态资源」把字号显式落到正文控件上
  （`NoticeSuspensionWindow.axaml` 的 `TextBox.notice-content`、`HomeworkSuspensionWindow.axaml` 的
  `SelectableTextBlock/TextBox.document-content`）：样式优先级高于主题默认值，且滚动中新生成的行同样生效。

**回归测试**（新增 `OverlayContentFontSizeTests`，窗口级 + 接线）：
- `通知窗正文字号_跟随悬浮窗字号`、`作业窗文档正文与编辑框字号_跟随悬浮窗字号`；
- `控制器应用设置_把字号转交给窗口正文`（用测试替身窗口验证控制器接线）。
