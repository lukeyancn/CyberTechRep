## 2. 逐条需求说明

### 2.1 需求 1：通知行控件改为「已读」下方

**行为口径**：通知悬浮窗每条通知的右侧操作区改为**垂直堆叠**——「已读 / 标记未读」在上、「转为作业」在下，整体右对齐、垂直居中（`Spacing=2`），两行都保持右对齐。

**边界与取舍**：只动布局容器与对齐方式，按钮的点击回调、文案、ToolTip、气泡提示、已读/未读两种视图下的按钮语义一律不变；`Grid.RowSpan=2` 让操作区跨内容行与元信息行，行高不因多出一行按钮而额外撑高。

### 2.2 需求 2：通知 ↔ 作业互转继承学科与来源

**行为口径**

- **模型层**：`NoticeItem` 新增 `SenderLabel`（来源发送者展示名）。通知界面**不显示**来源，该字段只为换类继承保留；旧数据为空时作业侧显示「成员」。
- **存储层**：`INoticeStore` 新增 `AddOrUpdateWithSourceAsync(..., senderLabel, subject, ct)`。接口带**默认实现**（回落到原 `AddOrUpdateAsync`，忽略来源名与显式学科），因此既有测试替身与第三方实现无需改动即可编译通过。
- **通知 → 作业**：通知已有学科时**一键直接继承**该学科，不再弹学科选择菜单；无学科（空 / 「未分类」）时保留原有的**兜底学科选择菜单**。文档条目一并带上来源展示名、成员与时间；正文里与继承学科一致的「学科：」前缀会被剥掉，避免出现「语文：语文作业……」这类重复。
- **作业 → 通知**（单条与整篇文档两个入口）：通知条目继承作业学科（含「学科：」前缀，重复执行幂等）与来源展示名（从作业文档条目里取；取不到则留空，界面按「成员」显示）。
- **换类覆盖语义不变**：仍写 `message-kind-overrides.json`，重投 / 断点续传不回摆；迁移顺序仍是「先写目标、再删原」。

**关键边界与取舍**

| 项 | 取舍 |
| --- | --- |
| 前缀剥离 | 只在**前缀学科与继承到的学科一致**时剥离，其他情况保持原文（比如通知前缀是「数学」而作业学科被改成「语文」，正文原样保留，由用户自行判断） |
| 「未分类」不写前缀 | 继承学科为空或「未分类」时**不传显式学科**，避免落出「未分类：」前缀；此时改走既有的成员绑定解析决定是否加前缀，与旧版行为一致 |
| 来源仅在作业侧 | 通知界面刻意不展示来源（视觉上更干净、也避免泄露发送者昵称）；来源只在作业文档条目里展示 |
| 幂等性 | 前缀剥离与加前缀都可重复执行：同一消息来回换类不会累积多个前缀 |

### 2.3 需求 3：未命中关键词 / 命中数相等一律归为通知

**行为口径**

- 新增常量 `NoKeywordHitNoticeReason = "no_keyword_hit_notice_default"` 与判定方法 `IsNoKeywordHitDefaultReason`（忽略大小写与首尾空白，允许带诊断后缀，但后缀以字母/数字/下划线开头时视为另一原因，避免误命中同前缀枚举值）。
- **计数相等 → 通知**：这条旧规则本来就成立（`count_tie_notice_default`），本次未改。
- **两侧均未命中且文本非空 → 通知**（旧行为是 `Unknown` = 消息被忽略）。旧版「消息直接消失」的观感由此消除。
- **AI 用途②（消息二分类「后补识别」）触发条件放宽**：从「未识别（Unknown）」放宽为「**未识别或关键词未命中**」，即默认归为通知的消息仍会给 AI 一次翻盘机会。
- **AI 用途③（无关键词兜底识别）保留**：管道在「默认通知」路径上先尝试兜底识别，命中可信学科则按作业归档（含文档追加与附件二次归档），**不写默认通知**；未启用 / 无文本 / 未得到可信学科则落回通知路径。

**关键边界与取舍**

| 项 | 取舍 |
| --- | --- |
| 空文本仍为 Unknown | **仅**「文本为空 / 纯媒体」与「分类异常」仍返回 `Unknown`，不生成空的「通知」条目。原因是空条目对老师毫无信息量，只会污染通知列表 |
| 纯文件 / 图片消息 | 走既有的**文件管道 + 学科选择悬浮窗**路径，完全不受本次改动影响（文件不会被当成「通知文本」落档） |
| 兜底识别失败 | 不投重试队列——兜底不改变「消息被忽略」的现状语义，避免同一条无关键词消息被无限重试 |
| AI 不可用 | 全部 AI 路径失败只降级回关键词链路，归类结果仍为「默认通知」，不丢消息 |

### 2.4 需求 4：作业文档方块撑满学科外框

**行为口径**：按 Fluent 主题的部件名清零内边距——`Style Selector="Expander"` 设 `Padding=0`，`Style Selector="Expander /template/ Border#ExpanderContent"` 设 `Padding=0, MinHeight=0`；白色文档方块自身 `Margin=0`、`BorderThickness=0`、`CornerRadius="0,0,4,4"`（底部圆角与外框展开态底角一致），内部 `Padding=8` 保留，文字不贴边。

**边界与取舍**：**表头与展开行为不变**——`ExpanderHeader` 独立使用主题的 `ExpanderHeaderPadding`，不受上述清零影响；外框自带的背景色 / 描边 / 圆角一律保留（半透明底色不变）。之所以按部件名定位而不是设置 `Expander.Padding`，是因为主题模板用 `TemplateBinding` 承接了 `ExpanderContentPadding` 与 `ExpanderMinHeight`，只改外层属性无法穿透到模板内部。

### 2.6 需求 6：学科圆圈右上角「有新文件」小红点

**行为口径**：新增 `SubjectFileBadgeTracker` 记录「哪些学科有新文件但用户还没看过」。圆圈列表项从纯字符串改为带状态的 `SubjectCircleItem`（学科名 + `HasNewFile`），右上角叠加红色小圆点（`IsHitTestVisible=False`，不抢圆圈的点击与拖放命中）。

- **标记**：文件归档完成（`FileUpdated` 且 `Status == Archived`）时标记该学科。
- **清除**：用户打开 / 切换到该学科的文件悬浮窗（`SubjectFilesController.SubjectFilesShown` 事件）后清除。
- **刷新策略**：列表里已有该学科 → 只改命中项的 `HasNewFile`（定项刷新，圆圈不闪烁）；列表里还没有该学科（首次出现）→ 整表刷新，并由 `SubjectFileBadgeTracker` 合并回未读标记，红点不丢。

**关键边界与取舍**：红点**仅在本次会话内有效、不持久化**——重启 ClassIsland 后已存在的文件不显示红点，只有重启后新归档的文件才点亮。这样可以避免重启后满屏红点（用户无法区分「新到的」与「历史上就有的」）；代价是「重启前没点开就重启」的提醒会丢失。

### 2.7 需求 7：多位未绑定学科的老师同时发消息

**行为口径**：新增 `SubjectSelectionQueue`（FIFO；同 `MessageId` 去重；上限 **100** 条，超出丢弃最旧一条，防止无人值守时无限堆积），配合逐条处理流程：

- 窗口**一次只显示一条**请求；后到的请求不再覆盖先到的内容，只刷新「**待处理 N 条**」计数。
- 用户点选学科、或点新增的「**跳过（暂不绑定）**」按钮后，推进到下一条；全部处理完自动收起窗口。
- 点选学科时依次完成三件事：① 写回成员学科绑定（全局作用域）；② 该消息的作业条目人工修正（`SubjectSource=Manual`，永不回退）；③ 该消息的文件二次归档到所选学科目录。**三件事全部完成（无论成功、失败还是抛异常）后才推进队列**，保证「一条都不丢、后面的老师不会被卡住」。

**边界与取舍**：写回失败只记日志，绝不影响消息主流程（消息早已按既有降级语义落库）；「跳过」不写任何绑定，只推进队列；同一 `MessageId` 重复入队只保留一条（短时间内的重投 / 重复事件不会占两个队列位）。

### 2.8 需求 8：学科文件悬浮窗图片缩略图

**行为口径**：新增 `ImageThumbnailProvider`——按扩展名判定图片、**限宽解码为 176px 缩略图**、最多缓存 **300 条**（超限整体清空，风格与既有 `FileIconProvider` 一致）。大图标视图与详细列表视图**都**接入：解码成功显示缩略图，失败（文件不存在、非图片、格式损坏、任何异常）一律**回落**原有的文件关联图标或「📄」占位，绝不抛异常。

**边界与取舍**：缩略图解码发生在 **UI 线程**（首屏一次性解码，文件多时首屏会有可感知的停顿）；SVG（矢量图）与无扩展名文件不参与缩略图，直接走图标回落。

### 2.9 需求 9：图片悬浮窗（第六悬浮窗）

**行为口径**

- **窗口**（`Views\ImageSuspensionWindow.*`）：标题栏为 `[打开] [⋯] [×]`（「打开」在 `⋯` 左侧）；正文为竖向列表，每张图片按窗口宽度**等比撑满**；多图累积（上限 **20 张**，超出丢弃最旧一张）、新图自动滚动到可见位置、同一文件记录重复到达则忽略（按记录 id 去重）。
- **「打开」语义**：用系统默认图片查看器打开「**当前正在看的图片**」= 视口中心最近的图片；判定不出来（布局未完成等）时回落**最新一张**；无图片时按钮禁用。
- **解码宽度**：按窗口宽度自适应并 clamp 到 **640 ~ 1600 像素**（窗口尚未显示时用 800 兜底）。
- **服务**（`Services\Overlays\ImageOverlayService.cs`，`IHostedService`）：订阅文件管道，仅处理**归档完成**的图片，经 UI 线程加入窗口；再按设置项 `Overlays.ImageAutoShowOnReceive`（默认开）决定是否自动弹出。
- **接线**：`SuspensionWindowController.ImageKey` 全链路（已知 key、设置读写、默认 `Visible=false` + 420×560、拖拽回写、旧 `overlays.json` 兼容）、`SettingsChangeApplier` 应用该窗设置、设置页新增「图片悬浮窗（收到图片自动展示）」区块（自动展示开关 + 窗口几何 / 层级 / 穿透 / 显示开关与复位按钮）、`Plugin` 注册窗口单例与 hosted service。

**关键边界与取舍**

| 项 | 取舍 |
| --- | --- |
| 20 张上限 | 防止长时间运行后位图累积吃内存；超出丢弃**最旧**一张（保留最近收到的，符合「看最新」的使用习惯） |
| 开关语义 | `ImageAutoShowOnReceive` **只控制「收到图片是否自动展示」**，不决定悬浮窗是否显示；悬浮窗显示与否由该窗自己的「显示悬浮窗」设置（`Overlays.Image.Visible`）与各悬浮窗同款机制控制。关闭该开关后图片仍会加入窗口数据，手动打开窗仍能看到 |
| 默认隐藏 | 该窗默认 `Visible=false`——避免开机就占用屏幕；收到图片时才自动展示 |
| 重复到达 | 同一文件记录（同一 id）重复事件忽略，不会出现重复条目 |
| 依赖 | 仅 Windows：`System.Drawing` 解码 + 系统默认查看器打开；非 Windows 平台相关分支直接返回 |

### 2.10 需求 10：上课联动延时

**行为口径**：新增设置 `SubjectCircleBarSettings.AutoOpenDelaySeconds`：

- **0**：准点（现状行为，逐条一致）——仅「正在上课 + 时间点已确认 + 真实科目」时立即评估。
- **正数 N**：**上课后推迟 N 秒**再用当前科目评估（一次性 `DispatcherTimer` 等待）。
- **负数 -N**：**上课前提前 N 秒**——订阅宿主主计时器节拍，在「尚未上课 + 下一节课是真实科目 + 0 < 距上课剩余时间 ≤ N」时立即按**下一节课科目**评估；去重键 =「下一节课科目名 + 该时间点开始时刻」，同一节课只提前触发一次；随后真正的上课迁移到达时沿用原有 `_lastOpenedSubject` 去重，不重复弹。

设置页在「圆圈栏排列与文件悬浮窗联动」区块新增 `NumericUpDown`（**-600 ~ 600，步进 5**），配文字说明。

**关键边界与取舍**

| 项 | 取舍 |
| --- | --- |
| 推迟等待期的取消行为 | 等待期间「**离开上课状态 / 科目变化 / 上课联动设置变化**」都会取消本次等待；等待到期后本课延时即视为已消耗，课中到达的文件归档事件恢复「立即评估补弹」的既有语义 |
| 高频保存不推后延时 | 设置变更只有「联动开关 / 延时值」真的变化才取消等待——否则悬浮窗拖拽位置回写等高频保存会把等待不断推后，延时可能永不到期 |
| 提前模式的触发条件 | 距上课剩余时间为 0（正在上课或没有下一节课）、下一节课科目非真实（哨兵 `???` / 「课间休息」/ 空白）一律不评估 |
| 非真实科目 | 延时三种取值下一律不评估（哨兵学科不会被当作真实科目弹窗） |
| 等待仅存在内存 | 推迟等待是内存态；宿主重启会丢失该次等待（重启后按启动对表逻辑重新评估当前状态） |

## 5. 已知边界与未验证项

| 项 | 说明 |
| --- | --- |
| 真机时序（上课联动） | `IsLessonConfirmed` 的确认时机、提前触发相对目标时刻的误差（**≤1 秒**，取决于宿主主计时器节拍）仅在模拟/单测层面验证，未在真实课表上测量 |
