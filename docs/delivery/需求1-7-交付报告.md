## 3. 方案选型说明

### 3.1 去重合并方案：归一化整段比对 + 行级 Jaccard 并集

选择**确定性集合对齐**而非编辑距离/语义相似度，理由：

1. 老师重复发作业的真实形态只有两种——「完全重发」（归一化后逐字相同）与「重发并补充」（行级超集/子集）。行级集合对齐能精确覆盖且结果可解释；
2. 编辑距离/语义相似度阈值难调，**误合并（丢作业）的代价远高于漏合并（多一行）**，故只在「行集合高度重叠」时合并；
3. 合并取并集并保留原有行顺序；用户手工编辑过的文本单独走 `ManualText` 增量追加，不因合并覆盖用户删改。

判定顺序（`HomeworkDocumentMerger.Plan`）：
- 归一化（全角→半角、去所有空白、ASCII 小写、统一标点）后整段相等 → `Duplicate`，不新增条目；
- 同一发送者（`MemberOpenId` 相同；旧数据两侧均为空视为同一）且行级 Jaccard ≥ `LineOverlapThreshold = 0.5` → `MergeIntoExisting`（并集）；
- 否则 `Append`。跨学科/跨老师绝不合并。

### 3.2 断点续传方案：游标为主 + 启动核对兜底

**游标结构**（`napcat-resume-cursor.json`，见 §5.1）记录「每群已成功入档到哪一条」。

- **去重键优先级**：消息 id → 时间 + 内容哈希（协议端未给 id / id 不稳定时兜底）。内容哈希输入 = **规范化后的事件 JSON**（`MessageRecord.RawJsonSnapshot`），时间 = **协议端原始 `time`**（`SourceTimestampUnix`）。
- **关键修复（本次）**：实时路径原实现用「本地接收时刻 + 拼接文本」计算稳定键，而核对路径用「服务端时刻 + 事件 JSON」，两套口径算出的键永不相等，`IsCovered` 的同秒兜底失效 → 重启核对可能重复补齐。现统一为：
  ```86:89:src/CyberTechRep.Plugin/Services/MessageAccess/MessageIngestService.cs
              var timestamp = message.SourceTimestampUnix;
              _resumeCursor.Record(
                  message.GroupOpenId, message.MessageId, timestamp,
                  NapCatResumeCursorStore.ContentHashKey(timestamp, message.RawJsonSnapshot));
  ```
  核对路径同步改用同一 `SanitizeRawSnapshot` 处理事件 JSON（`NapCatBackfillService.cs:288-291`），保证两条路径的哈希输入逐字节一致。
  另一处修复：协议端未提供 `time` 时，旧实现会用本地时刻推进时间线，导致真实时间更早的历史消息被误判为「已覆盖」而<b>漏补</b>；现 `SourceTimestampUnix == 0` 时只按消息 id 去重、不推进时间线。
- **原子性**：写入走 `JsonStoreFile.SaveWithBackup`（临时文件 + 原子替换 + `.bak` 备份），崩溃/强杀最多丢「最后一次 1 秒防抖刷新之前的增量」；游标只在消息成功交给管道后单调推进，不会超前。
- **偏差处理**：游标落后 → 核对窗口重读一段，靠幂等 + `recentKeys` 只补不重；游标超前（人为编辑存档）→ 核对窗口重读最后 N 条并靠幂等收敛。
- **可容忍边界**：单群缺口 > 核对窗口（默认 100 条，可调）无法补齐——属「插件长时间离线且群消息超过窗口」场景，已知边界。

## 4. NapCat 撤回事件查证结论

**结论：能收到，但仅限协议端上报的撤回。**

- OneBot 11 定义 `notice.notice_type = group_recall`（群）与 `friend_recall`（私聊），NapCat 实现了这两个上报；本插件已接入（`NapCatEventNormalizer.TryMapRecall`，`NapCatEventNormalizer.cs:126-172`）。
- **局限（已如实声明，未假装实现）**：NapCat 存在**非 API 撤回不上报**的已知缺陷（上游 issue #1171）——即非本插件发起、由客户端撤回的消息，部分版本不会推送 `group_recall`。因此不能保证 100% 收到。
- **替代方案（已预留并实现）**：
  1. 手动删除：作业文档条目与通知条目均可在悬浮窗删除；
  2. 可选核对兜底：`ConnectionSettings.RecallReconcileEnabled`（**默认关闭**）——定期用 `get_msg` 探测当日已归档消息是否仍存在，不存在则视为已撤回并删除；因消息超期后 `get_msg` 也会失败存在误判风险，需用户显式开启；
  3. 撤回联动总开关 `RecallSyncEnabled`（默认开）。

## 5. 字段定义

### 5.1 续传游标 `NapCatResumeCursorEntry`（`napcat-resume-cursor.json`）

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `groupId` | string | 群号（私聊为 `private:{user_id}` 占位） |
| `lastMessageId` | string | 已入档的最后一条消息 id（稳定键优先） |

### 7.1 本轮修复记录（复核阶段）

复核时全量回归暴露 2 条失败用例（`ReplyChain_RepliedHomework_AppendsToRepliedSubject_NotClassifierSubject`、`ReplyChain_RepliedNotice_WritesNoticeArchive`），根因与修复：

- **根因**：`ProcessMessageCoreAsync` 原顺序是「先跑消息分类器 → 再解析回复链」。回复消息一旦分类器不可用（AI 未配置/故障）就被整条丢弃，落不到回复链；即使分类器可用，回复消息也被无谓地跑了一遍识别链（且 `classifier.CallCount` 不为 0，与「回复链优先」的语义不符）。
- **修复**：`MessageDispatchService.cs:247-305` 重排为「文件段入队 → 人工换类覆盖查询 → 回复链归并 → 消息分类器」。回复链命中即落档返回，**完全不调用分类器**；人工换类覆盖（需求 5）优先于回复链，避免用户手动改过的消息被回复链摆回原类型；有覆盖记录时同样跳过分类器（显式语义无需再判定）。
- **另修（需求 7 收尾）**：`MaintenanceSettingsPage.axaml.cs:255-285` 暂停滚动期间不再替换绑定文本——此前暂停只停自动滚动，文本仍每 300 ms 重排，TextBox 光标/滚动会被拽走，与「暂停滚动」语义不符；现在暂停时视图完全冻结、日志继续进环形缓冲，恢复后由下一拍一次性补齐（序号基线未推进，必然重排一次，不漏行）。

## 8. 遗留风险与后续建议

| 风险 | 影响 | 建议 |
| --- | --- | --- |
| NapCat 非 API 撤回不上报（issue #1171） | 部分撤回无法自动删除 | 已提供手动删除 + 可选 `get_msg` 核对兜底（默认关，因超期误判风险） |
| 单群缺口 > 核对窗口（默认 100 条） | 长期离线且消息量大时可能漏补 | 可在连接设置调大 `NapCatBackfillCount`，代价是首次同步耗时线性增长 |
| 通知悬浮窗可交互区域为「并集外接矩形」 | 行间空隙也会捕获鼠标（过度捕获，不影响选择） | 如需精确，可改为矩形列表逐项命中 |
| `WS_EX_NOACTIVATE` 下键盘 Ctrl+C 可能无效 | 键盘复制不可用 | 已提供右键「复制/全选」菜单兜底；如仍需要键盘复制，可考虑在区域内临时激活窗口 |
| NapCat 模式发送目标必须是数字群号 | 填 OpenID 会失败 | 已给出可操作错误提示（`Send_NapCatMode_NonNumericTarget_ReportsActionableError`），设置页已写明 |
| 官方平台无历史消息补拉 API | 官方模式无断点续传 | 能力缺口已声明；官方平台由服务端保证投递 |
